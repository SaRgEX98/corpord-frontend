# План развития поиска маршрутов, карт и календаря цен

Дата: 2026-11-01. Статус: предложение для продуктового и технического ревью.
Документ передаёт требования команде разработки; описанные API и функции ещё
не реализованы. Изменения поставляются отдельными PR в `dev` обоих репозиториев.

## 1. Цель и зафиксированные требования

Пассажир выбирает город или место отправления и назначения из понятных подсказок,
видит остановки на карте, выбирает дату с доступными рейсами и актуальной ценой.
Интерфейс продолжает использовать shadcn-vue/Reka и существующие цвета Corpord.
Календарь русскоязычный, неделя начинается с понедельника. Диалог завершения всех
сеансов расположен в центре экрана. Цена может увеличиваться при спросе;
правила задаёт сервер, изменения цены объясняются пользователю.

Под «маршрутами» здесь понимаются направления, остановки и поиск рейсов.
Изменение URL и маршрутизации Nuxt само по себе не решает эти задачи.
Заказы и платежи не включаются автоматически в этот этап; учёт занятости требует
отдельного достоверного источника, указанного ниже.

## 3. Подсказки и рекомендации

Для первой версии нужна система ранжирования по правилам, без ML. Статус столицы
может быть основанием для стартового приоритета Москвы, но сам по себе не является
измеренной популярностью. Список «Популярные направления» должен опираться на
обслуживаемые направления, затем — на агрегированную статистику поиска и поездок.

Правила выдачи:

1. Без ввода показывать обслуживаемые популярные города. Начальный приоритет
   настраивается редактором: Москва получает высокий приоритет, если обслуживается.
2. При вводе сначала учитывать точное совпадение и префикс, затем опечатки/синонимы;
   популярность разрешает близкие по релевантности варианты. Запрос «Тю» не должен
   уступать Москве только из-за её стартового приоритета.
3. После выбора «Откуда» ранжировать «Куда» по существующим направлениям из этой
   точки, включая допустимые промежуточные участки; выдавать регион и тип места.
4. Различать город, остановку/автовокзал и внешний адрес/POI. Совпадение города
   с местом посадки не предполагается. Внешнее место связывать с обслуживаемыми
   остановками явно; при неоднозначности предложить выбор остановки.
5. Для Москвы без рейсов не обещать доступность: в поиске городов допустима
   пометка «Нет рейсов», но в блоке доступных направлений его не показывать.
6. Одинаковые названия различать по региону и внутреннему ID. Свободный текст
   не становится выбранным местом, пока не разрешён в однозначную сущность.
7. Геолокацию использовать только по действию пользователя; при отказе оставить
   обычный поиск. Персональную историю и ML вынести в последующее развитие.

Технически: debounce около 250–350 мс, отмена предыдущего запроса, защита от
запоздалых ответов, до 10 подсказок, клавиатура и экранный диктор. Порог вызова
провайдера настраиваемый (начально 2 символа). Начальная локальная выдача работает
без стороннего API. Изменение отправления перепроверяет назначение и календарь.

Собирать агрегированные события показа/выбора подсказки, поиска, пустой выдачи,
открытия рейса. Не сохранять полные частные адреса в аналитике популярности.
Ввести фильтрацию ботов и повторов; поисковые события не использовать напрямую
для повышения цен. Оценивать качество по доле успешных поисков и пустых выдач,
а не только по кликам на первую позицию.

## 4. Внешние карты, адреса и места

Рекомендуемый кандидат для пилота — единый стек Яндекс Карт: карта, Геосаджест,
геокодирование. Это архитектурное предложение, а не уже выбранный договор.
Геосаджест поддерживает географические объекты и организации согласно
[официальной документации Яндекса](https://yandex.ru/maps-api/docs/js-api/object/geosearch/index.html).
Пилот проверяет качество именно автовокзалов, остановок и адресов нашего покрытия.

| Вариант | Роль в проекте | Что проверить до выбора |
| --- | --- | --- |
| Яндекс Карты + Геосаджест + Геокодер | Основной кандидат для карты и подсказок мест | Качество остановок, тариф, права на хранение/отображение, доступность |
| 2ГИС Map API + Search/Suggest | Альтернатива для карты и объектов | Покрытие городов/межгорода, ограничения договора, качество POI |
| DaData | Возможное дополнение для нормализации российских адресов и идентификаторов | Нужна ли нормализация сверх основного провайдера; дополнительная стоимость |

[2ГИС Suggest](https://docs.2gis.com/en/api/search/suggest/overview) предлагает
объекты по поисковому запросу. [DaData Address Suggestions](https://dadata.ru/api/suggest/address/)
возвращает структурированные адресные данные, в том числе идентификаторы ФИАС;
это не замена интерактивной карте и не источник расписания Corpord.

Не подключать сразу несколько платных подсказчиков без результатов пилота.
Начальный набор для сравнения: 30–50 запросов по текущим направлениям, Москве,
одинаковым названиям, неполным адресам и опечаткам. Проверить выбор POI → адрес →
координаты → остановка, стоимость на ожидаемом объёме и поведение при отказе.
Никакие тарифы и бесплатные лимиты в этом плане не считаются гарантированными;
[условия Яндекса](https://yandex.ru/legal/maps_api/ru/) проверить для конкретной
конфигурации до включения интеграции.

Архитектура интеграции:

- Go API предоставляет единый контракт геопоиска через адаптер провайдера.
  Секретные ключи остаются на сервере. Браузерный ключ SDK карты, если нужен,
  публичен по назначению: ограничить домены/продукты/квоты.
- Внутренние ID городов и остановок отделены от внешних ID. Хранение внешних
  ответов, координат и сроков кэша допускается в пределах выбранного договора.
- Ограничить частоту публичных запросов, длину строки и таймаут, ввести метрики
  ошибок/задержек/расхода квоты. При отказе использовать собственный справочник
  остановок и понятное сообщение; не подменять координаты вымышленными.
- Карту загружать по необходимости, синхронизировать выбранную остановку с
  адресом. Текстовый список остановок доступен и без карты.
- Линия между остановками обозначается как схема. Реальную дорожную геометрию
  получать отдельно; не выдавать прямую линию за путь автобуса и не менять
  расписание автоматически по оценке времени стороннего маршрутизатора.

## 5. shadcn, цвета и окно завершения сеансов

Использовать shadcn-vue/Reka: Combobox/Command + Popover для подсказок,
Select для сортировки и селекторов, Calendar + Popover для даты, AlertDialog
для подтверждения завершения сеансов. Недостающие компоненты добавить в
`app/components/ui`; не переносить React-компоненты в Vue-приложение.
Рекомендации сверены с документацией [Calendar](https://www.shadcn-vue.com/docs/components/calendar)
и [Dialog](https://www.shadcn-vue.com/docs/components/dialog).

Единый источник цвета — `main.css`, а не новая палитра:

| Токен | Светлая тема | Тёмная тема |
| --- | --- | --- |
| primary | `#245ce3` | `#6d9aff` |
| background | `#f5f6f8` | `#0e1724` |
| card / popover | `#ffffff` | `#172436` |
| foreground | `#172538` | `#e9eff8` |
| muted | `#edf1f6` | `#213047` |
| border | `#e1e6ed` | `#2c3c52` |
| destructive | `#b83232` | `#ff9696` |

Селекторы, раскрытые списки, hover, выбранное значение, disabled и focus используют
семантические токены Tailwind/CSS. Проверить все селекторы, включая административные
формы и выбор месяца/года. Доступность и повышенную цену обозначать текстом/иконкой,
а не только цветом. Новые семантические статусы согласовать с существующей темой.

AlertDialog монтируется через Portal, центрируется относительно viewport по двум
осям, имеет overlay и безопасные отступы на мобильном. Высота ограничена viewport,
содержимое прокручивается при необходимости. Начальный фокус — «Отмена», фокус
удерживается внутри и возвращается на кнопку после закрытия. При отмене API не
вызывается; подтверждение отправляет ровно один logout/all. Во время запроса кнопки
заблокированы, ошибка остаётся в окне, повтор разрешён. Сохранить существующие
защиты сессии и честное объяснение текущего ограничения: refresh отзываются,
уже выданный access token действует до TTL.

## 6. Календарь, расписание и доступность

- Григорианский календарь, `ru-RU`, понедельник первым; русские месяцы/дни недели,
  ввод/показ `ДД.ММ.ГГГГ`, время 24 часа, рубли в `ru-RU`.
- Дата поиска — локальный день отправления выбранной остановки, не день
  устройства пользователя. Хранить IANA timezone города/остановки; моменты рейса
  передавать RFC3339, дату запроса — `YYYY-MM-DD`. Прибытие показывать по месту
  прибытия с пояснением, если пояс отличается. Не приравнивать всю РФ к Москве.
- Запрашивать сводку за видимый месяц для выбранной пары и числа пассажиров
  (для MVP по умолчанию 1). Запрос ограничен диапазоном; не скачивать все рейсы.
- День содержит минимум актуальной цены подходящего участка и статус:
  «Есть рейсы», «Нет рейсов», «Мест нет» либо «Доступность уточняется».
  Loading/error/unknown отличаются от подтверждённого отсутствия рейсов.
- Минимум цены считается только по допустимым рейсам и выбранному участку,
  с тем же составом цены, что в выдаче. Отменённые и уже отправившиеся участки
  исключаются; для промежуточной остановки учитывать её время отправления.
- Если мест не учитывают, показывать наличие расписания и «Свободные места
  уточняются». Не отображать число свободных мест как вместимость автобуса.
- Дни без рейсов недоступны для выбора с понятным объяснением. При ошибке
  загрузки позволить повтор; отсутствие ответа не блокирует календарь как «нет рейсов».
- Смена направления/месяца отменяет старый запрос; смена фильтров инвалидирует
  цену. Выбор дня открывает согласованную выдачу; устаревшая цена перепроверяется.

## 7. Цены и спрос

Сначала ввести единый серверный расчёт цены участка и денежную модель: RUB,
целые копейки в API, точное хранение в БД, без расчётов через `float64`.
Правило совместного использования `base_price` и `price_to_next` описать в ADR;
рекомендуется явный тариф участка, исключающий двойное сложение полной цены рейса
и цен остановок. Миграция должна сохранить существующие значения и совместимость
старого клиента до переключения.

Динамическое ценообразование вводить по этапам:

1. Единая актуальная цена для календаря, выдачи и карточки; базовый тариф,
   расписание сезонных/выходных тарифов и ручные корректировки с аудитом.
2. Повышение по проверяемой загрузке и времени до отправления, только после
   появления достоверного учёта мест. При отсутствии данных — базовый тариф.
3. Другие сигналы спроса и автоматическая оптимизация — после накопления данных
   и отдельного ревью. Сам факт повторного поиска не повышает цену пользователю.

Расчёт должен иметь версию правил, даты действия, нижнюю/верхнюю границу,
ограничение частоты изменений и журнал причины. Например, коэффициенты загрузки
и времени применяются к тарифу участка и ограничиваются пределами; численные
пороги/коэффициенты определяет продукт, они не утверждены этим документом.
Одинаковые параметры поездки дают одинаковую цену всем пользователям в один момент.

Для реального учёта остатков нужен либо интегрированный источник перевозчика,
либо контур продаж/резервов: активные брони с TTL, оплаченные места, отмены и возвраты,
сериализация конкурентных операций. Участки `[A,B)` и `[B,C)` не пересекаются;
бронирование A→C занимает оба, остаток A→C определяется на всём участке.
API вместимости без этих данных недостаточно. Это отдельная backend-зависимость,
а не обязательство реализовать всю оплату в PR календаря.

Ответ цены содержит сумму, валюту, время расчёта, версию и, где применимо,
срок действия quote. В первой информационной версии quote не гарантирует место.
При будущей покупке сервер атомарно перепроверяет/фиксирует цену и остаток на
согласованный TTL; при изменении сообщает новую сумму до подтверждения действия.
UI показывает «от … ₽» в календаре и краткую причину повышения, когда оно есть.
Полная цена включает обязательные сборы; неподтверждённые скидки не вычитаются.

## 8. Предлагаемый контракт и данные для технического проектирования

Пути ниже — предложение под `/api/v1`, их ещё нет. Перед реализацией оформить
OpenAPI и ADR, согласовать пагинацию, ошибки и backward compatibility.

| Операция | Вход | Выход |
| --- | --- | --- |
| `GET /locations/suggest` | q, origin_id, типы, limit | внутренний ID, тип, название, регион, обслуживается ли, причина ранга |
| `GET /geo/suggest` | q, город/область поиска | временный ID провайдера, тип, подпись; при необходимости отдельное разрешение координат |
| `GET /locations/{id}/stops` | выбранный город/место | допустимые остановки, адреса, координаты, timezone |
| `GET /trips/search` | from_id, to_id, date, passengers, sort, cursor | рейсы с участком, статусом, тарифом, доступностью и пагинацией |
| `GET /trips/calendar` | from_id, to_id, month, passengers | timezone, все дни месяца, min_price_minor/null, статус, рассчитано в, версия |
| `POST /trips/{id}/quote` | посадка, высадка, passengers | актуальная цена, объяснение, доступность и срок действия |

Данные: внутренние города/места и связи с остановками, нормализованное название
и регион, timezone, внешние ссылки при разрешении хранения, тарифы участков,
версии правил и аудит, агрегаты популярности. Запретить высадку до посадки,
одинаковые точки и невалидные даты; определить переходы ошибок 400/404/409/429/503
и единые машинные коды. Ограничить горизонт календаря/размер страницы.
Quote не создаёт заказ и не резервирует место автоматически.

| 2. Backend | Города/остановки/timezone, миграции, адаптер геопоиска, лимиты | Пилот провайдера и собственные подсказки |
| 3. Backend | Поиск участков, серверная пагинация, единая цена и календарная сводка | Модель денег/тарифов и справочники этапа 2 |
| 4. Frontend | Подсказки, карта, календарь цен, фильтры в URL, согласованная выдача | Backend этапов 2–3; без фиктивных остатков |
| 5. Backend + интеграции | Достоверные остатки из перевозчика/резервов, конкурентность | Выбран источник мест; затем подключить статусы в UI |
| 6. Backend + продукт | Правила повышения по загрузке, аудит, лимиты, выключатель | Этап 5 и утверждённая политика; сначала теневой расчёт |
| 7. QA + reviewer | Интеграционное ревью, браузерная приёмка и исправления | Отдельная тестовая БД/аккаунты и sandbox провайдера |

На каждом этапе команда описывает проблему, поведение после изменения, контракт,
миграции, результаты проверок и ограничения. Каждый PR направляется в `dev`,
проходит CI и ревью до merge; frontend и backend связываются ссылками на зависимые
PR. Нельзя включать зависимый UI раньше готовности контракта. Документный PR
не означает одобрения всех будущих реализаций. Сроки оценивать после ADR и выбора
источника мест, не обещать календарь реальных остатков до решения этой зависимости.

Публикация образов и развёртывание — отдельный шаг после merge и успешного CI.
Перед миграциями нужна свежая резервная копия. Флаги карты/нового поиска/динамических
цен позволяют выключать возможности независимо; откат тарифных правил возвращает
базовую цену, миграция денег требует отдельного совместимого плана отката.

## 10. Критерии приёмки и проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Пустой запрос / «Мос» / «Тю» | Обслуживаемые популярные города; Москва при релевантности; Тюмень по совпадению |
| Москва без рейсов; два города с одинаковым именем | Нет обещания доступного рейса; регион и ID различают города |
| Выбран город, вокзал или внешний адрес | Однозначная точка поиска либо явный выбор обслуживаемой остановки |
| Быстрый ввод и смена направления | Старый ответ не заменяет новую подсказку/цену |
| Поиск через промежуточные остановки | Посадка раньше высадки, цена и время относятся к выбранному участку |
| Русский календарь в браузере с английской локалью | Русские подписи, Пн–Вс, ДД.ММ.ГГГГ, 24-часовое время |
| Рейс около полуночи, устройство в другом поясе | День поиска определяется остановкой отправления; пояс явно показан |
| День с рейсами, sold out, отмена, unknown, ошибка API | Различимые состояния; min price только среди допустимых рейсов |
| Выбор дня → выдача → карточка | Одинаковый состав цены; при обновлении честное сообщение о новой цене |
| Нет источника остатков | Показ расписания, доступность уточняется; нет вымышленных чисел |
| Изменение спроса и ручная корректировка | Серверные границы и аудит соблюдены; выключатель возвращает базовый тариф |
| Два конкурирующих резерва последнего места | При внедрении резервов успешен максимум один, освобождение TTL проверено |
| Светлая/тёмная/system, mobile и клавиатура | Селекторы и popover в токенах; читаемость, фокус, нет горизонтального скролла |
| Диалог logout/all после прокрутки на desktop/mobile | Центр viewport, видимые действия, focus trap; отмена без запроса |
| Ошибка и двойное нажатие logout/all | Одна операция, ошибка в диалоге, безопасный повтор, прежние session guards работают |
| 429/таймаут провайдера, недоступная карта | Поиск собственных остановок и текстовые адреса продолжают работать |

Frontend: `npm run typecheck`, `npm test`, `npm run build`, браузерные сценарии
Playwright на изолированном стенде; скриншоты 390px и desktop в обеих темах,
проверка клавиатуры/экранного диктора. Backend: unit расчёта цены и времени,
контрактные тесты, PostgreSQL-интеграции миграций и участков, race/concurrency для
остатков, тесты rate limit/таймаутов адаптера с подменой провайдера.
Не расходовать платную квоту в обычном CI. Новые проверки запускать для каждого
реализационного PR; исторические PASS не подтверждают будущий функционал.

Предварительные цели производительности: p95 внутреннего suggest ≤300 мс,
календарной сводки ≤700 мс на согласованном наборе данных; задержку внешнего
провайдера измерять отдельно. До реализации зафиксировать нагрузочный профиль
и исходные значения. Контролировать долю пустых поисков, ошибки внешнего API,
стоимость запросов, расхождения цен и переходы к карточке рейса.

## 11. Решения, которые остаются открытыми

Предлагаемые допущения MVP: РФ и текущие направления, один пассажир, поиск прямых
рейсов и их участков, Яндекс как кандидат пилота, расписание без обещаний мест,
единая цена на сервере, затем учёт остатков и динамические правила.

До активации соответствующего этапа продукт и техлид фиксируют:

- Провайдера, бюджет и разрешённое хранение геоданных по результатам пилота.
- Период продаж и календарный горизонт, поддержку нескольких пассажиров,
  пересадок и международных направлений (последние два вне исходного MVP).
- Источник фактических мест: перевозчик или собственные резервы/продажи.
- Семантику базовой цены и тарифов участков, обязательные сборы, TTL цены,
  пороги повышения и пределы тарифа.
- Источник начальных приоритетов городов, период агрегации популярности,
  объём/срок хранения аналитики.

Эти вопросы не мешают исправить центрирование диалога, унифицировать селекторы
и подготовить контракты. Полноценная ML-рекомендация не является условием запуска.
