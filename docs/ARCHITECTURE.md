# Архитектура frontend

Актуально на 2026-10-31. Приложение — Nuxt 4 SPA (`ssr: false`), Vue 3,
TypeScript, Pinia, Tailwind 4 и существующие UI-примитивы Reka/shadcn.
Серверный источник данных — Go/Gin API с PostgreSQL; frontend не дублирует
бизнес-правила хранилища и не добавляет фиктивные заказы или бронирования.

## Слои и зависимости

1. `app/types/domain` описывает точные read/input-модели backend. DTO
   авторизации находятся в `app/types/dto`. Relation ID и отображаемые названия
   различаются типами; краткая карточка рейса и подробный рейс имеют разные модели.
2. `app/api/transport.api.ts` — фабрика типизированных сервисов ресурсов с
   внедряемым transport. Она отвечает за пути, HTTP-методы и нормализацию списков.
   `app/api/auth.api.ts` описывает авторизацию и профиль.
3. `app/api/session-client.ts` конфигурирует ofetch, Bearer-заголовок,
   HttpOnly cookie и восстановление сессии. Nuxt-плагин связывает клиент с Pinia.
4. `useTransportApi()` предоставляет сервисы страницам. Страницы управляют
   загрузкой, пустыми состояниями, формами и повторным чтением после изменений.
   Общая админ-форма использует метаданные ресурсов; особенности контракта
   остаются в типизированном API, а не выводятся из URL или текста интерфейса.
5. `useAuthStore` хранит текущие token/user и предоставляет действия авторизации.
   `useAuth` выдаёт реактивный интерфейс для UI. Обещания текущей инициализации
   и чтения профиля находятся вне сериализуемого состояния Pinia в WeakMap.
6. `apiErrorMessage` переводит transport-ошибки в понятные сообщения, показывает
   доменную ошибку и скрывает детали внутренних ошибок сервера.

Состояние справочников/таблиц локально странице: API пока не поддерживает
пагинацию, фильтры и инвалидацию кэша. Добавлять глобальный query-cache следует
вместе с серверной пагинацией или необходимостью согласованного обновления
нескольких экранов. Вложенные данные рейса читаются одним запросом backend.

## Сессия и права

Access token хранится в памяти; localStorage не используется для токенов.
Refresh token доступен только backend через HttpOnly cookie. Все запросы отправляют
`credentials: include`. На первом переходе `ensureSession()` восстанавливает
access token и профиль. Один Promise инициализации обслуживает все одновременные
вызовы, включая публичную навигацию после перезагрузки.

Ротация refresh token объединена для явного refresh, инициализации и конкурентных
401. Запоздалый 401 от старого access token повторяется с уже обновлённым token,
не запуская новую ротацию. Защищённый запрос повторяется максимум один раз и только
после 401. Сетевые ошибки и 5xx не повторяются: запись могла уже завершиться.
Неверный пароль, регистрация, refresh и обычный logout не запускают recursive refresh.

Маршруты `/me` и `/admin` требуют загруженного профиля; административные страницы
дополнительно используют middleware `admin` и возвращают 403 роли `user`.
Публичные страницы доступны при отсутствии сессии. `auth/callback` самостоятельно
выполняет refresh, поэтому глобальная инициализация его пропускает.
Сервер остаётся источником проверки прав: UI не получает права из формы/URL.

## Развитие и ограничения

Форматы дат отправляются backend в RFC3339; UI переводит локальный ввод времени
через `Date.toISOString()`. Денежная модель пока `number` вслед за Go `float64`;
переход на decimal/minor units требует согласованного изменения backend.

SSO связывание аккаунтов, серверная пагинация, роль пользователя при редактировании,
самостоятельное изменение профиля, бронирование и заказ отсутствуют в текущем API.
Их реализация требует backend-контракта до включения соответствующих действий UI.

Проверки контрактов работают без сети и БД на Node.js >=22; тесты с подменённым
fetch проверяют реальное поведение библиотеки ofetch. Они дополняют проверку
типов и production-сборку Nuxt; интерактивный SSO требует отдельных ручных проверок.
